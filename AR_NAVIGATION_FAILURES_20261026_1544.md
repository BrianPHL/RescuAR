## Confirmed causes

1. **MLD was blocked after successful retrieval.** A54 MLD routes were accepted at 15:48:56.600 (269.8 m) and 15:58:16.297 (256.3 m). The first registered publication was rejected at 15:48:58.446 with `physical road alignment pending`. Its 260 placement samples all report invisible geometry; the renderer receives no drawable route segments. There are 199 placement samples whose reason is `Waiting for a camera-matched road image`. A15 reports the same publication rejection after accepting MLD at 15:49:40.823.
2. **The road-image consumer uses the wrong coordinate assumption.** `ArCoreService.RoadSurface.cs` expected the raw semantic image to already match portrait viewport coordinates and aspect ratio. Google's reference semantic renderer explicitly transforms display coordinates to texture coordinates before sampling the semantic image. The old combined rejection also required equal image timestamps, although both images are acquired from the same ARCore Frame and their timestamp equality is not part of the documented pairing contract. The capture only records a generic combined rejection, so it does not establish which individual condition failed on each phone. The fix applies the SDK transform and logs dimensions and timestamps separately; it does not guess a rotation from aspect ratio.
3. **Independent UI checks erased valid geographic text.** `UpdateTurnGuidance` could generate geographic recovery text, but `RefreshTurnGuidancePanelForCurrentState` demanded an available AR route window and explicitly hid MLD text whenever `MldPathIsCurrent()` was false. `TryShowMldRecoveryState` also hid the card. The road-image blockade therefore caused persistent AR failure and immediately disappearing text through two separate paths.
4. **GPS uncertainty was treated as progress.** `RoutePositionObservationPolicy` allows innovations inside combined reported accuracy plus a 2 m motion allowance. That is a consistency check, not a stationary filter. `NavigationStabilityPolicy` likewise checks plausibility, not proof of walking. `RouteProgressTracker` commits forward matches; `GpsPdrFusionPolicy` permits confidence-weighted forward corrections and later repeated backward corrections. All can be valid independently while allowing a stationary distance to advance and retreat.
   - A54 `logcat-002.txt:3513`, 15:50:38.771: committed progress changes from 20.757 to 30.816 m, while paired camera displacement between the two fixes is only 0.0444 m. Accuracy changes from 6.5 to 14.07 m. Fusion action is `AcceptForward`.
   - Same file, line 3980, 15:50:54.092: progress changes from 30.816 to 27.816 m while camera displacement is 0.1631 m. Fusion action is `CorrectBackward`.
   - Seven consecutive sample pairs have less than 0.5 m tracked displacement and more than 1 m committed progress change. This is evidence of the reported fluctuation; it does not imply that the user stood still during the entire walk.
5. **Several displayed meter values meant different things.** Route distance comes from committed progress, while destination-vicinity notices directly formatted raw GPS-to-destination distance. Those notices could fluctuate even when route progress was held. The vicinity notice now describes proximity without presenting a second precise-looking meter count. Genuine arrival/hazard notices retain priority over turn instructions.

The capture does **not** establish duplicate active GPS progress loops as the cause. A54 loops start and exit per trip. The A15's MLD loop belongs to process 353; its following AStar loop belongs to process 5437, rather than a second loop competing in the same process. Cancellation and destination-version checks guard asynchronous results. Separate consumers and UI visibility rules are real; duplicate subscriptions were not demonstrated.

## Road-image capture, GPS, Wi-Fi and A-GPS

- **Automatic road semantics:** `ConfigureRoadSemantics` enables local ARCore Scene Semantics when supported. `PublishRoadSurface` reads a road/sidewalk label image and confidence image. `SemanticRoadBoundaries` and `RoadSurfaceAlignment` estimate local road edges against verified ground. This is an optional physical alignment refinement, not route retrieval or GPS positioning. Both tested devices reported semantic support. A road mask may still be unavailable, ambiguous or incomplete without affecting geographic text or otherwise qualified GPS/AR geometry after this fix.
- **Diagnostic photo capture:** `RequestCpuDiagnosticCapture` / `TryCaptureCpuDiagnosticImage` acquire YUV data and optionally save a JPEG. That separate diagnostic request is not a prerequisite for routing, progress or AR tracking. The user does not need to take road photos.
- **Visual tracking:** ARCore itself uses camera images and motion sensors for local pose/ground. It is separate from the road-classification result and from the diagnostic JPEG. A GPS coordinate cannot replace camera orientation, perspective, floor height or continuous local tracking.
- **GPS and assisted location:** the application requests MAUI `GeolocationAccuracy.Best` from Android. It does not implement its own Wi-Fi localization, A-GPS configuration, or Google fused-location dependency. Android/network assistance may help supply or acquire geographic location, but the application has no evidence that a particular returned reading used Wi-Fi or A-GPS; current telemetry reports provider unavailable. Those sources cannot replace semantic road-edge recognition or AR pose tracking. They also cannot guarantee curb-level absolute alignment while stationary.
- No Geospatial authorization, Cloud project, subscription, manual alignment step, new dependency, or required walking calibration was added.

## Focused changes

- Added `RouteProgressMotionPolicy` for both algorithms; stationary filtering is applied after GPS/fusion classification and before committing corrected trip distance. Raw readings remain available to independent heading, matching and arrival checks.
- Decoupled text visibility from AR-window/MLD-path availability, retained a clear uncertainty state, and evaluated text maneuver distance at accepted progress.
- Removed the mandatory visual-road publication veto while retaining shared heading/tracking/GPS/hazard/registration gates. GPS-only placement carries an approximate-placement notice. This restores eligibility; it does not certify physical accuracy.
- Added `SemanticImageCoordinates` to reproject paired labels/confidence with ARCore's actual texture transform before road-boundary fitting. Added rejection diagnostics for image sizes/timestamps.
- Removed a raw meter count from proximity notices; proximity detection and arrival evidence are unchanged.

## Short two-device acceptance procedure

Run on both phones with the new candidate, first MLD then AStar, using the same destination and street. Start the field logger before opening guidance and record the screen if available.

1. Away from the destination-vicinity zone, allow the initial location to settle, then stand for 60 seconds and slowly rotate the phone. **Expected:** accepted route distance remains steady rather than repeatedly jumping several meters; text remains visible. Position uncertainty displays a held-distance status instead of silently clearing the card.
2. Aim at the road with usable lighting and normal AR tracking while still standing. **Expected:** qualified geometry can appear without waiting for a road-classification result; automatic road refinement may improve it when usable edges are observed. Turn the phone and check that geometry remains tied to the physical scene rather than following the screen. Correct road placement is an acceptance requirement; an approximate-placement banner alone does not pass this check.
3. Walk 20–30 m and stop again. **Expected:** distance decreases with actual movement and settles when stopped; a turn instruction changes when route progress reaches its maneuver, rather than when an AR window refreshes.
4. Approach the selected evacuation center. **Expected:** the proximity/arrival notice still appears and can legitimately replace the turn card. Poor accuracy remains unconfirmed; no automatic arrival is inferred from the filtered display distance.

Report which phone/algorithm failed, approximate time, and the new archive. If geometry remains hidden, new road-image dimensions distinguish image acquisition/transform failure from missing edges; placement/heading/identity telemetry distinguishes those from renderer failure. If geometry is visible but displaced, that remains a physical-registration failure and must not be described as fixed by these builds.
